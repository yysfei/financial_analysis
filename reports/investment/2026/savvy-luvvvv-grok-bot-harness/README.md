## 结论

[@savvy_luvvvv](https://x.com/savvy_luvvvv/status/2124114560290267555) 的 X 长文《直接抄我的 Grok Bot 配置：完整的 Harness 文件夹》，讲的是如何用 **1 个共享文件夹 + 4 个角色席位 + 2 类 Jev 判定 + 6 个 Bot 的群聊**，避免「同一个模型既写代码又给自己打分」。这个分工思路本身成立，11 条提示词也完整出现在长文代码块里，不是只有配图。

但它**不是**「复制提示词就能省一半钱的现成系统」，更不是交易系统。三个已经核对过的事实，足以把「今晚复制、明天开跑」从可直接执行改成有条件实验：

1. **Grok Bot 官方没有模型选择器。** [官方 FAQ](https://docs.x.ai/grok-bot/faq) 写明：用户不能指定或避开某个模型，界面也不展示底层模型；用量按 Grok Bot 使用计量，不按模型名计价；「把任务路由到 Opus 5.5 也不会改变你的每 token 费用」。因此，文中给顾问/验证者绑定 grok 4.7、侦察员绑定 grok 4.3、构建者绑定 grok build 0.1，并据此比较 $0.82 对 $1.58，是按 **xAI 公开 API 标价**做的纸面拆分，并不对应 Grok Bot 产品的实际计费方式。
2. **构建者所依赖的 `grok-build-0.1` 已在 API 上下线。** [xAI 发布说明](https://docs.x.ai/developers/release-notes) 记载该模型于 **2026-11-19** 结束生命周期，不再经 API 提供。长文发布于两天后的 2026-11-21。即便历史上 $1 / $2 的标价是对的，按这个型号去复现「构建者输出只要三分之一价格」，现在已经做不到。
3. **Jev 不是 Grok Bot 内置功能。** 文中的 `jev_seat.py`、`jev_done.py` 要调用 TypeSafe 的决策模型 Jev（`Noul` / `Choice` 题型）。官方价格与延迟与正文相符，但长文几乎不提这是第三方 API、需要密钥和预付余额。提示词 1 只要求创建一行占位的 `.py` 文件，「先什么都别填」。没有可运行的客户端，所谓分流和完工判定就是空的。

配图是设计过的信息图，不是 Grok Bot 运行界面或账单截图。图 8 用「17/17 检查通过、P(done) 0.95、提交 `a41f9c2`、命令 `k6 run upload_burst.js`」展示一个限流功能示例，时间为 2026-11-16 14:32；作者没有给出对应的公开仓库，无法核验这次运行是否真实发生。回复里 [@Dzzzzzer](https://x.com/Dzzzzzer/status/2124189836496023809) 问「为什么搭建了 grok bot harness 消耗的额度更快了」——这与官方说明一致：群聊里每个 Bot 的回复、以及 Bot 之间的私信，都会计入用量，Bot 越多通常越费额度。

**有条件可行的范围：** 已经有 Grok Bot、只做带测试的软件任务、由人写好可核对的 `GOAL.md`、自己实现并限制 TypeSafe 调用、把发送/删除/付款/发布留在人工审批，并且不指望文中的 $0.82 账单。  
**不可行的范围：** 把它当成已验证的省钱系统、交由通用助手无人值守跑完、或改造成自动交易台。

## 机制核验

### 已独立核验（A）

- **共享云电脑、不能当安全边界：** [Grok Bot FAQ](https://docs.x.ai/grok-bot/faq)：「你账户下的每个 Bot 使用同一台持久云电脑」，共享文件、浏览器会话和登录；「不要把不同 Bot 当作安全边界」。与正文一致。
- **一屏一次电脑操作、故需多个构建者：** FAQ：「一个 Bot 在自己的屏幕上，一次只能跑一个电脑操作任务。」三个构建者 Bot 的理由成立。
- **群聊人数 2 到 6：** [协作文档](https://docs.x.ai/grok-bot/chat-and-collaboration) 写明 `To:` 栏加入 two to six Bots。本方案用满 6 个，不超限。
- **账户大约 50 个 Bot：** [《Designing Grok Bot》](https://x.ai/news/designing-grok-bot) 原文是 “practical limits of roughly 50 Bots per account and six per group chat”。正文的「最多 50 个」与「约 50」相符，不是硬编码出现在 FAQ 里的精确配额表。
- **群聊会推高用量：** 同一篇协作文档：「每一条 Bot 回复都计入用量，包括群里的回复和 Bot 之间的消息，所以群里 Bot 越少，回复通常越少。」
- **定时任务存在：** 官方产品支持 Routines；把周五审计写成定时任务，在产品能力上说得通，但本轮没有实际创建。
- **grok 4.7 / 4.3 公开 API 标价，以及 200K 以上整笔请求按更高档计费：** 与 [定价页](https://docs.x.ai/developers/pricing) 和 [Grok 4.3](https://docs.x.ai/developers/models/grok-4.3) / [Grok 4.7](https://docs.x.ai/developers/grok-4-7) 文档一致。正文提醒侦察员把单次读取压在 200,000 token 以内，方向正确。
- **历史上的 grok-build-0.1 标价确为 $1 / $2：** [模型页](https://docs.x.ai/developers/models/grok-build-0.1) 与 [上线说明](https://x.ai/news/grok-build-0-1) 一致；输出价格正好是 grok 4.7 输出价 $6 的三分之一。但同上，该型号已于 2026-11-19 在 API 上下线。
- **Jev 的价格、延迟和题型：** [TypeSafe 模型文档](https://docs.typesafe.ai/models) 与 [帮助中心](https://help.typesafe.ai/articles/5187202169-how-much-does-jev-cost) 写明：输入 $0.042 / 百万 token，输出免费；默认每题上下文 32k（每请求 64k）。InfoQ 对 TypeSafe 的报道引用官方 70–500 ms 延迟。[Cloudflare 文档](https://developers.cloudflare.com/ai/models/typesafe/jev/) 给出 `noul` 题返回概率值。正文里的价格、延迟、「noul」「最多读 32,000 token」与官方大体相符。更精确的官方限制是每题 32k、每请求 64k；加特殊头可升到 262k，但更慢、更不准。

### 作者声称、未能独立复现（C）

- 「一个功能、五轮，$0.82 对 $1.58，约省 48%。」图 7 注明「token 数是我们自己的」。没有发票、用量页或可复现日志。图 7 把 66,000 token 构建者输出画成 $0.40（按 $6/百万）对 $0.13（按 $2/百万），算术与公开 API 标价相符（B：66,000 × 6 / 1,000,000 = 0.396），但不能证明某次真实 Grok Bot 运行花了这些钱。
- 正文写「14 次分流大约十分之一美分，换成 grok 4.7 写文字大约 8 美分」；图 7 写成「14 次选席位 + 5 次判完成」为 $0.002 对 $0.131。数量级相近，数字并不相同。
- 「100 次同样功能」折算 $157.69 对 $81.79，只是把上面的单次数字乘 100，没有新证据。
- 图 8 的 17 项凭证、提交 `a41f9c2`、时间 2026-11-16 14:32，没有配套仓库，不能当成已完成项目的验收记录。
- 0.80、0.92、最多 6 轮是作者设定的阈值，没有校准数据。Jev 只根据 `GOAL.md`、凭证**文件名列表**和验证报告打分，不读凭证内容和代码；文件名存在不等于测试真的通过。
- 标题是「直接抄我的」配置。在该帖之前，用 `jev_seat.py` / `jev_done.py` / `P(done)` 等确切字样检索，没有找到更早的英文原文。同一套数字（$0.82 / $1.58、11 条提示词、6 个 Bot）在次日 2026-11-22 09:55:03 Asia/Shanghai 被 [@oreillnw](https://x.com/oreillnw/status/2124320724089516229) 改写成《别让 AI 自己给自己打分：6 个 Grok Bot 防烧钱流水线》。Jev 分流、GOAL.md、凭证和独立验证者，在 2026 年的 Grok Bot 内容里已经很常见，不能据此证明作者是发明人。

### 未知或与官方冲突（A 与 C 对照）

- **不能按席位锁定模型。** 这是对方案核心成本假设的直接否定，见上引 FAQ。把「模型：grok 4.3」写进席位文件，最多是提示词偏好，产品不保证遵守，也不按该标价扣费。
- **Grok Bot 的钱不是按这次 API 标价逐次结算的。** 新客户走 The X Subscription 时，Grok Bot 从与 Cursor / Grok 应用共享的**每周用量池**里扣；用超之后才是预付额度或按需用量。旧版 Cursor 套餐同样是每周额度，用尽后若开启 on-demand 才从 Cursor 另计。因此即使用更便宜的底层模型，也不自动等于账单减半。
- 提示词要求不可逆操作写入 `/workspace/approvals`。这是好的约定，但只是指令遵循，不是强制执行。官方还指出：审批、密钥和登录请求**不会出现在群聊里**。
- 「验证者从不看构建对话、全新上下文」只能隔离聊天记忆。它们仍在同一台电脑上，可以看到工作区文件、测试输出和 git 历史，并不是物理隔离的验收环境。

## 成本、资金、极端损失与合规

- **交易成本/滑点：** 本案没有市场成交。真正的「成本」是 Grok Bot 每周额度、超额按需费用，以及 TypeSafe 预付余额。六个 Bot 并行、互发消息、多轮循环，可能比单 Bot 更快耗尽额度；至少有一条公开回复提出了这个问题。
- **资金与密钥：** 实现 Jev 需要 TypeSafe API 密钥，且会落在这台**共享**云电脑上。官方明确不要把多 Bot 当成隔离边界。任何交易密钥、交易所登录或钱包，都不应该放到这套共享环境里。
- **极端损失：** 软件任务上，主要风险是循环空转烧掉额度、错误改文件、或 Bot 忽略「先问你」的规则去发送、删除、付款、发布。提示词把第 6 轮熔断和审批文件夹写进去了，但没有强制闸门。若把这套东西改去交易，损失就是仓位和密钥被误用，原文并没有为此设计交易所风控。
- **合规：** 原文是工程方法文，本身不是投资建议。作者同一账户还在推广「24/7 交易 agent」「开源盈利策略库」「零员工月入 15 万美元」等材料，并把本长文拿去引用。那些是另一类宣传，未在本评估中当作已验证收益。

## Bot 实现评估

这不是交易策略，不存在「专用下单程序 vs 通用助手自动交易」的选择。若只讨论要不要在 Grok Bot 里落地这套工程流水线：

| 部分 | 判断 | 难度 |
| --- | --- | --- |
| 复制 11 条提示词、建 6 个 Bot、开 6 人群聊、写 `GOAL.md` | 通用 Grok Bot 可以协助起草，但创建 Bot、拉群和设定时任务必须由用户在产品里完成；本评估没有代做 | 低到中 |
| `jev_seat.py` / `jev_done.py` | 应做成**确定性**小程序：调用 TypeSafe `POST /v1/systemone`，校验选项，按阈值分流或停机，把结果写入 `seats.log`；不要让模型「随便写一个完成分数」。需要用户自己的 TypeSafe 密钥和消费上限 | 中 |
| 验证者重跑测试、写凭证 | 测试命令本身应是确定性的；「验证者 Bot」仍然是通用模型，可能漏跑、误写凭证或读到不该看的文件 | 中 |
| 按席位锁定 grok 4.7 / 4.3 / build 0.1 并按 API 标价省钱 | **与官方「无模型选择器、不按模型名计价」冲突**，不应作为实现目标 | 不可按原文实现 |
| 用这套流水线自动交易或连接钱包 | 排除。通用助手不持有私钥、不下单。若将来有人要做执行，只能是隔离的确定性程序，且不在本研究授权内 | 不做 |

开发部署的阻塞点不是提示词不够，而是：Jev 客户端未提供、构建者型号已下线、Grok Bot 不能按席位锁模型、群聊可能更快消耗额度、以及指令遵循代替不了强制审批。即使条件满足，也只适合小范围、可测试、有人工熔断的软件任务。
